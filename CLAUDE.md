# CLAUDE.md — xewe-os-build-toolchain

Build/flash/release/format tooling for ESP32 Arduino firmware projects. It is developed here
and **installed into projects by copying `scripts/` and `tools/code_formatter/` into `<project>/build/`**
(done by the project's own `setup.sh`, e.g. xewe-os). Everything in this
repo must work for any project; project-specific data never lives here.

## Three roots

Every script resolves these from its own location (`scripts/common/paths.sh`, Windows:
`scripts/windows/_paths.ps1`), never from the caller's CWD:

| Variable | Default | Holds |
|---|---|---|
| `TOOLCHAIN_ROOT` / `$ToolchainRoot` | two levels above `scripts/common` (`<project>/build`) | scripts, tools |
| `BUILD_ROOT` / `$BuildRoot` | `TOOLCHAIN_ROOT` | project data + generated state |
| `PROJECT_ROOT_DEFAULT` / `$ProjectRoot` | parent of build root | `.ino`, `Config.h`, `src/` |

Overrides: `XEWE_BUILD_ROOT`, `XEWE_PROJECT_ROOT`.

Rules:
- Never write paths like `../../build_config` or rely on `cd` into the script dir. Use
  `SCRIPT_DIR` + `paths.sh`, call sibling scripts as `"${SCRIPT_DIR}/x.sh"`.
- Scripts that run `git`/`gh` against the project must `cd "$(get_cfg project_root)"` first
  (see `release.sh`), and resolve user-supplied relative paths before that `cd`.
- `build_config` (bash) and `build_config.ps1` are generated by `setup.sh` / `setup.ps1` into
  `BUILD_ROOT`. All other scripts read paths through `require_build_config` + `get_cfg <key>`.
  Adding a key means updating **mac, linux and windows** setup scripts.

## Project data vs toolchain

| In the project's `build/` (not in this repo) | In this repo (installed into `build/`) |
|---|---|
| `.gitignore`, `release_matrix.csv`, `required_libraries.txt`, `version_state` (committed) | `scripts/`, `tools/` |
| `build_config*`, `.venv/`, `libraries/`, `builds/` (ignored) | |

`setup.sh` / `setup.ps1` create `release_matrix.csv`, `required_libraries.txt`, `version_state`,
the `.ino` and `Config.h` only when missing; never overwrite a project's own files. They append
the installed and generated paths to `build/.gitignore`; keep that list the same on all platforms.

## Scripts

- `scripts/mac/*.sh` is the bash implementation. `scripts/linux/*.sh` are one-line forwarders to
  it, except `setup.sh` (apt-based) and `install_arduino_esp32.sh`.
- `scripts/windows/*.ps1` mirror the mac scripts; there is no Windows `release`.
- Flow: `setup` → `build` (injects `PROJECT_NAME`, `BUILD_VERSION`,
  `BUILD_TIMESTAMP` and optional `--config_json` `#define`s into `Config.h`)
  → `compile` (arduino-cli, output in `builds/<ts>-<ver>-<chip>-<project>/`, `builds/latest`
  symlink, merged `.bin`, `manifest.json` for ESP Web Tools, `meta.json`) → optional `upload`
  (esptool, merged image at 0x0; a successful upload bumps PATCH in `version_state`)
  → `listen_serial`.
- `release.sh`: prompts for a version ≥ `version_state`, builds every `release_matrix.csv` row
  (`CHIP` column required; other columns become `Config.h` defines and nested output folders;
  `_BUILD_NOTES` is notes only), writes `<project>/static/firmware/releases/<version>/`, then tags
  `v<version>` in the project repo and creates a GitHub release with the archive.
- `tools/code_formatter/format.py`: clang-format plus custom layout stages. With no paths it
  formats `$XEWE_PROJECT_ROOT/src` (set by `format.sh` / `format.ps1`).

## Changing things

- Keep scripts runnable from any CWD and from their installed location in `<project>/build/`.
- A change that renames a `build_config` key or moves a file breaks projects until they re-run
  setup; say so in the commit message.
- Test new bash with `bash -n`; PowerShell cannot be run here, so mirror bash changes carefully
  and keep Windows path logic in `_paths.ps1`.
- Releases of this repo: tag `vX.Y.Z` on main so projects can install a fixed version
  (xewe-os: `setup.sh --toolchain-ref vX.Y.Z`).
